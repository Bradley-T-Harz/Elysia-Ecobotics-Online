# Governed-function preservation floor

Status: Phase 1 owner-review material. This is not runtime authority, a public status manifest, or permission to alter any capability.

## Preservation rule

The third-pass investigation identified 512 evidence-backed governed-function **candidates** under its atomic-function definition. The Canonical Website Doctrine and Canonical Website Plan adopt that inventory as the minimum known preservation floor for this navigation project.

The number is not an acceptance shortcut. It does not mean that all 512 candidates are live, enabled, production-configured, globally navigable, permanently distinct, or covered by focused tests. It does not verify the historical estimate of 529. Owner and domain review may combine, split, reclassify, or add records without weakening the obligation to preserve the underlying outcomes and boundaries.

Every later navigation phase must therefore be evaluated route by route and behavior by behavior. A header entry is only a doorway; changing the doorway is not authority to change the room.

## Status and evidence limits

- Source presence proves that code, a route, a contract, a test, or documentation exists; it does not by itself prove current production availability.
- Route registration is owned by `src/App.tsx` and is recorded separately in `route-preservation-contract.json`.
- Eligibility and authorization remain owned by participation contracts, authenticated roles/capabilities, ownership and reviewer assignment, backend controls, RLS, RPCs, Workers, APIs, feature configuration, and provider-confirmed state.
- Public status language requires a separately owner-approved status manifest. This project must not invent badges or compress live, partial, planned, unavailable, test-mode, restricted, profile-dependent, participation-dependent, or feature-gated states.
- Runtime verification requiring an account, role, provider, production binding, or protected record remains outside Phase 1.

## Protected-boundary checklist

Before any later visible change can pass its gate, review must confirm:

1. No known outcome in any of the eight families was removed, disabled, hidden as a substitute for authorization, or represented with a stronger availability claim.
2. The exact route, alias, dynamic-record source, query/hash/location-state behavior, and direct-load expectation remain intact.
3. No red-zone internal file changed.
4. No orange-zone behavior, schema, policy, endpoint, binding, provider configuration, legal body, or data flow changed.
5. No restricted metadata entered the anonymous public navigation bundle.
6. The homepage body, footer, account behavior, router, unknown-path behavior, and existing protected-room entry pages remain unchanged unless a later gate explicitly authorizes a narrowly scoped exception.

## Reconciliation note

This summary intentionally does not duplicate 512 investigative records into runtime source. Owner approval of this floor does not constitute final approval of every candidate’s atomic boundary. The preserved source inventory remains review evidence; the route contract and its tests provide the implementation-facing guardrail for Phase 1.
